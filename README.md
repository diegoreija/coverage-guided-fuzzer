# coverage-guided-fuzzer

A coverage-guided fuzzing engine built from scratch in pure Python — no AFL, no libFuzzer, no external fuzzing library. It targets Python parsers and protocol handlers, tracks code coverage via `sys.settrace`, and uses that feedback to mutate inputs toward unexplored code paths instead of generating random bytes blindly.

---

## Why this exists, and an honest note on scope

Industry-standard coverage-guided fuzzers (AFL++, libFuzzer) work by instrumenting **compiled C/C++ binaries** at the compiler level, and find **memory-corruption bugs** (buffer overflows, use-after-free) — the interpreter or CPU itself has no memory safety, so a malformed input can literally corrupt program state.

This project targets a different, legitimate class of software: **Python parsers and protocol handlers**, the kind of custom service you run into on a CTF/HTB/THM box that isn't a web app — a bespoke binary or script speaking its own text protocol. Python is memory-safe, so a fuzzer here can't find buffer overflows; what it finds are **unhandled exceptions**: parsing logic bugs, unbounded recursion (denial-of-service), and edge cases in input validation. That's a real, legitimate bug class — it's just a different one from what AFL hunts in C.

The core algorithm — track which code was reached, keep inputs that discover new code, mutate them further, discard inputs that don't add anything new — is implemented here from first principles using nothing but the Python standard library. Understanding and building that feedback loop yourself is the point of the project, not wrapping an existing tool.

| | AFL++ / libFuzzer | coverage-guided-fuzzer |
|---|---|---|
| Target | Compiled C/C++ binaries | Python functions (parsers, protocol handlers) |
| Instrumentation | Compiler-level (SanitizerCoverage, AFL passes) | `sys.settrace` at the interpreter level |
| Bug class found | Memory corruption (overflows, UAF, double-free) | Logic errors, unbounded recursion, unhandled edge cases |
| Dependency | AFL++/Clang toolchain | Python standard library only |

## How it works

```
 seed corpus
      │
      ▼
 pick a seed ──► mutate (bit flip / insert / delete / overwrite / splice)
      │
      ▼
 run target(mutated_input) under sys.settrace
      │
      ├── crashed (unhandled exception)? ──► record, deduplicate by signature, score severity
      │
      └── didn't crash, but reached NEW (file, line) pairs? ──► add to corpus as a new seed
      │
      ▼
 repeat
```

1. **Coverage tracking** (`engine/coverage_tracker.py`). Wraps a single call to the target function in `sys.settrace`, recording every `(filename, line)` pair executed, restricted to the target's own source file so standard-library noise doesn't drown the signal.
2. **Corpus management and mutation** (`engine/corpus_manager.py`). Holds every input that has ever expanded the total coverage frontier. New candidates are generated by mutating an existing corpus entry — bit flip, byte insert/delete/overwrite, or splicing two entries together — rather than generating fully random bytes each time.
3. **Crash triage** (`engine/crash_classifier.py`, `engine/severity_scorer.py`). Crashes are deduplicated by a signature built from the exception type and the exact line that raised it, so a campaign that finds the same bug 500 times reports it once, with the smallest triggering input kept as the representative case. Each unique crash gets a preliminary severity label.
4. **Campaign orchestration** (`engine/campaign_manager.py`). Ties the loop together and returns aggregate statistics: iterations run, corpus growth events, total coverage reached, unique crashes found.

See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for the full design rationale, including why BFS-style breadth in mutation strategy was chosen and what a production-grade version would add (energy scheduling, dictionary-based mutation, etc.).

## Requirements

- Python 3.10 or higher
- No external dependencies — the engine is intentionally dependency-free

## Usage

```bash
python3 main.py \
  --target targets.toy_ftp_parser \
  --function parse_command \
  --seeds "USER:admin" "NEST:5;CRASHME" "HELLO" \
  --iterations 100000 \
  --seed-value 7
```

| Option | Description |
|---|---|
| `--target` | Python module path containing the target function (must be importable) |
| `--function` | Name of the function to fuzz; must accept a single `bytes` argument |
| `--seeds` | Initial seed strings (encoded as UTF-8 bytes) |
| `--iterations` | Number of fuzzing iterations to run |
| `--seed-value` | RNG seed, for reproducible campaigns |

See [`examples/sample_campaign_run.md`](examples/sample_campaign_run.md) for a full annotated run against the included example target, including the two real bugs it found on this exact target.

### Fuzzing your own target

Any Python function with the signature `def my_function(data: bytes) -> None` that raises on bad input can be fuzzed — point `--target`/`--function` at it. This is exactly the scenario described in the project's motivation: a custom protocol handler you find on a CTF box, once you have the source or can replicate it locally.

## Design decisions

- **`sys.settrace` instead of the `coverage` package.** The standard `coverage` library is built for test-suite reporting across a whole run, not for a tight loop needing a fast per-execution coverage set to diff against a running frontier. Writing the tracer directly keeps the engine dependency-free and gives full control over what's measured.
- **Deduplication by exception type + exact raise line, not by input.** Hundreds of different mutated inputs commonly trigger the exact same underlying bug; without this, a report would be flooded with duplicates of one real issue.
- **Uniform random seed selection**, not AFL-style energy scheduling (which biases toward seeds that have historically produced more new coverage per execution). This is a documented simplification — see Limitations below.

## Limitations

- **No energy scheduling.** Every corpus entry has an equal chance of being picked as the next mutation parent, regardless of how "productive" it has been. AFL uses a scoring system (execution speed, coverage gained, input size) to bias toward more promising seeds — this engine doesn't, which is a meaningful gap for larger targets.
- **No dictionary-based mutation.** Constructing exact numeric strings or magic tokens through byte-level mutation alone is inefficient — on the included example target, the engine reliably finds the `IndexError` and `ZeroDivisionError` bugs, but did **not** find the `RecursionError` bug within 100,000 iterations, because it requires mutating a numeric field ("count") to a specific large magnitude, which single-byte mutations rarely construct by chance. This is a real, honestly-documented gap, not a hidden one.
- **Targets memory-safe code only.** By design, this cannot find memory-corruption bugs — for that class of vulnerability, a compiled-target fuzzer (AFL++ against a C/C++ binary) is the right tool, and this project's coverage-tracking approach doesn't apply.
- **Single-process, sequential execution.** No parallel fuzzing workers; iteration count is bounded by single-core Python interpreter speed.

## Roadmap

- [ ] Energy scheduling based on execution speed and coverage gained per seed
- [ ] Dictionary-based mutation (inject known "interesting" tokens/magic numbers, not just byte-level mutation)
- [ ] Persistent corpus storage between runs, so campaigns can resume
- [ ] Optional integration path documented for AFL++ against compiled targets, for when memory-corruption bug classes are in scope

---

## Responsible use

This engine only executes the target function you point it at, inside the same Python process — it makes no network calls and doesn't touch any system beyond running the code you provide. Still, any bug it finds in third-party software should only be reported through the appropriate disclosure channel, and only against software you're authorized to test.
